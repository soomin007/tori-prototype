# 토리 프로토타입 개발 계획

> 상태: 기획 미확정. 이 문서는 "조작 테스트용 뼈대"만 다룬다. 스테이지, 스토리, 엔딩은 팀 회의 뒤에 따로 정한다.
>
> 발표는 2026년 12월 14일 주다. 날짜별 일정과 범위를 줄이는 기준은 10절에 있다.
>
> 2026-11-25에 스택 버전과 물리 가정을 직접 돌려 확인하고 문서를 고쳤다. 실측 수치는 7.3에, 다시 밟기 쉬운 함정은 `known-issues.md`에 있다. 실측에 쓴 스크립트는 `docs/spikes/tail-chain.mjs`다.

## 1. 목적

- 기획이 확정되기 전에, 확정과 상관없이 필요한 부분(몸 이동, 꼬리 물리, 꼬리 자르기와 회귀 구조)을 먼저 만든다.
- 팀원(기획 담당, 디자인 담당)이 링크로 직접 만져 보고 꼬리 조작 방식을 고를 수 있게 한다. 게임에 익숙하지 않은 사람도 첫 화면 안내만 보고 해 볼 수 있어야 한다.
- 기능마다 실제로 얼마나 손이 가는지 확인해서, 회의에서 범위를 정할 근거로 쓴다.

## 2. 기획 문서 기준 현재 방향 (미확정)

구현에 영향을 주는 것만 적는다. 2026-11-25 팀 회의록까지 반영했다. 회의록에는 뒤집힌 내용이 섞여 있어서 아래쪽(최근) 기록을 기준으로 읽었다. 회의록은 팀 내부 문서라 저장소에 넣지 않는다.

- 2D 횡스크롤. 스테이지 단위로 진행하고, 스테이지마다 배경이 다르다. 배경이 달라져서 과거로 돌아왔다는 것이 보인다.
- 처음부터 끝까지 플레이하는 데 10분 안팎이다.
- 주인공은 꼬리가 달린 도마뱀 토리. 꼬리로 물건을 붙들거나 길을 넘고, 꼬리로 공격한다. 핵심 조작은 "토리를 이동시키고 꼬리를 직접 다루는 것"이다.
- 꼬리를 자르면 과거로 돌아간다. 자르는 것은 플레이어의 선택이고 최대 세 번이다. 자를 때마다 더 이전 시점으로 돌아가고 꼬리가 짧아진다.
- 자른 자리에서 다시 자란 꼬리는 무늬가 다르고, 다시 자란 부분은 자를 수 없다. 길이를 얼마나 되찾는지는 정해지지 않았다.
- 과거로 돌아가면 모아 둔 아이템은 사라진다. 플레이어가 익힌 조작 실력은 남는다.
- 회귀할수록 도와주던 친구 NPC가 사라진다. 첫 회귀 뒤에는 일부가, 두 번째 회귀 뒤에는 거의 전부가 보이지 않는다. 같은 길인데 상황이 달라져 전과 같은 방법으로는 풀 수 없게 된다.
- 꼬리 길이에 따라 할 수 있는 일이 달라진다. 긴 꼬리는 균형을 잡고 멀리 닿기 좋지만 방향을 바꿀 때 늦게 따라오고 주변에 걸린다. 짧은 꼬리는 좁은 곳에서 돌기 쉽지만 균형을 잡거나 닿기가 어렵다.
- 실시간 전투가 있다(맵에 배치된 적, 꼬리 공격). 턴제는 검토했다가 접었다. 전투까지 어려운 조작을 요구하면 피로해진다는 걱정이 회의에서 나왔다.
- NPC와 대화해 조작법과 힌트를 얻는다. 대화나 상황에 따라 갈래가 생긴다.
- 실시간 타임어택은 뺐다. 넣는다면 NPC에게 말을 걸어야 시각을 알 수 있는 이야기 속 시계로 하고, 시각을 확인할 때 저장되게 하자는 이야기가 있었다(미정).
- 마지막 스테이지의 보스전, 꼬리가 있어야 가능한 비행, 꼬리를 다 자르면 날 수 없게 되는 엔딩은 이야기 중이다(미정).
- 그림은 픽셀 아트가 아닌 쪽이다(팀원 의견. 꼬리의 세부가 보여야 한다).
- 전하려는 것(회의록에서 되풀이되는 말): 돌아가서 고친 삶도 더 나은 삶이 아니라 다른 삶이고, 되감을 때마다 이전의 삶과 만남이 사라진다. 이 메시지는 자르기와 회귀에서 플레이어가 잃는 것(꼬리, 아이템, 친구 NPC)에 실린다. 뼈대에서는 M3의 "잃는 것이 느껴지는가"가 그만큼 중요하다.

## 3. 이번에 만들지 않는 것

스테이지 실제 제작, 스토리와 대사, 보스, 엔딩, 비행, 시간 시스템, 갈래 흐름도 화면, 실제 그림, 사운드.
다만 나중에 붙이기 쉽도록 자리(인터페이스, 데이터 형식)는 만들어 둔다.

## 4. 골라 볼 수 있게 만들 것

정해지지 않은 항목은 하나로 정하지 않고 실행 중에 바꿀 수 있게 한다.

| 항목 | 선택지 | 방식 |
|---|---|---|
| 꼬리 조작 | A: 마우스로 직접 / B: 평소 자동 + 키로 동작 | 첫 화면, 튜닝 패널에서 전환 |
| A 방식의 커서 | 절대(커서 위치를 꼬리가 쫓음) / 상대(포인터 잠금, 마우스 움직인 만큼 이동) | 튜닝 패널 |
| A 방식의 꼬리 구동 | IK 자세 추종 / 꼬리 끝만 당김 | 튜닝 패널(개발자용) |
| 꼬리 공격 판정 | A: 휘두르는 속도 / B: 키를 누르면 휘두르기 동작 | 조작 방식에 딸림 |
| 꼬리 길이별 능력 | 남은 구간 수마다 표로 정의 | `src/config/abilities.json` |
| 자를 수 있는 횟수, 구간별 마디 수 | 숫자 | 설정값 |
| 회귀 지점 | 자른 횟수로 정해짐 / 플레이어가 고름 | 설정값(기본: 자른 횟수) |
| 회귀 때 남는 것과 사라지는 것 | 상태 항목마다 지정 | `src/state/schema.ts` 한 곳 |
| 체크포인트가 생기는 때 | 스테이지 입장 / 특정 NPC와 대화 / 둘 다 | 설정값 |

조작 방식 A와 B는 M2 뒤 팀 회의에서 하나를 고를 때까지 같은 완성도로 유지한다. 고른 뒤에는 고른 쪽만 다듬는다.

## 5. 기술 스택

- TypeScript + Vite
- Phaser 4(4.1 이상): 렌더링, 씬, 입력, 카메라, 글자. WebGL 렌더러. Phaser 물리 엔진은 쓰지 않는다. Phaser 3과 달라진 API는 패키지에 함께 들어 있는 `node_modules/phaser/skills/`(`v3-to-v4-migration`, `v4-new-features` 등 28개 폴더)에서 확인한다.
- Rapier 2D(`@dimforge/rapier2d-compat`): 물리 전부. WASM이 패키지 안에 들어 있어 Node 테스트에서도 그대로 돈다(Node 26에서 확인). 쓰기 전에 `await RAPIER.init()`.
- lil-gui: 튜닝 패널
- Vitest: 로직 테스트, 헤드리스 물리 테스트
- GitHub Actions → GitHub Pages: `main`이나 `dev`에 푸시하면 두 브랜치를 테스트, 빌드해서 한 번에 자동 배포. Vite `base: './'`.

2026-11-25 기준 최신 버전은 phaser 4.2.1, @dimforge/rapier2d-compat 0.21.0, vite 8.3.8, vitest 5.1.2, lil-gui 0.21.0, typescript 7.0.2이고, 개발 PC는 Node 26.13, npm 11.20이다. M0에서 이 버전으로 설치해 `package-lock.json`으로 고정하고, GitHub Actions의 Node도 26으로 맞춘다. Vite 8, Vitest 5, TypeScript 7은 나온 지 얼마 안 된 큰 버전이라, 설정 파일 형식은 기억에 기대지 말고 공식 문서를 확인한다. `tsconfig.json`에는 `skipLibCheck: true`를 넣는다(known-issues 5번).

고른 이유: 꼬리는 관절 여러 개가 이어진 체인이고 몸무게를 버텨야 해서 관절이 튼튼한 물리 엔진이 필요하다. 또 Node만 있으면 어디서든 빌드와 테스트가 돌아가고, 팀원에게는 금방 열리는 링크 하나로 공유할 수 있다.

Godot와 Unity도 견줘 보고 웹 스택을 유지했다(2026-11-25). 개발자 한 명이 Claude Code로 만들고 발표까지 3주인 프로젝트라, 코드와 물리 동작을 터미널에서 숫자로 검증할 수 있는 쪽이 빠르다. 엔진을 쓰면 장면 편집과 실행 확인이 편집기 안에서 일어나 이 검증이 끊긴다. 팀원이 설치 없이 링크로 바로 해 볼 수 있다는 점도 웹이 낫다. 엔진의 장점인 레벨 편집기는 스테이지를 만들 때 LDtk로 메운다(11절).

## 7. 핵심 설계

### 7.1 물리 공통

- 물리는 미터 단위로 계산하고 `PPM`(1미터당 픽셀) 상수 하나로 화면에 옮긴다. 자리값은 화면 1280×720, PPM 100이다(화면에 가로 12.8m, 세로 7.2m가 보인다).
- 고정 스텝 1/60초. 프레임 사이 남는 시간은 누적해서 처리한다. 한 프레임에 최대 5스텝까지만 돌리고 그보다 밀린 시간은 버린다(탭을 떠났다 돌아왔을 때 몰아서 돌지 않게).
- 그릴 때는 직전 스텝과 현재 스텝의 위치와 각도를 누적 시간 비율로 보간한다. 보간이 없으면 120Hz, 144Hz 모니터에서 꼬리가 떨려 보여 조작감 비교가 흐려진다.
- 솔버 반복 횟수(`numSolverIterations`)는 설정값이고 기본은 16이다. Rapier 기본값 4로는 꼬리가 늘어난다(7.3).
- 충돌 그룹: 지형, 몸, 꼬리, 물건, 적, 감지 영역(NPC, 아이템, 체크포인트). 꼬리는 자기 몸과 부딪히지 않는다.

### 7.2 토리 몸

- 몸통(캡슐)과 머리를 동역학 바디로 만들고 회전 관절로 잇는다. 머리는 조금 흔들린다.
- 몸통은 바닥에 닿지 않고 떠서 간다. 몸통에서 아래로 레이캐스트를 쏘아 바닥까지의 거리를 재고, 스프링과 감쇠 힘으로 정해진 높이에 띄운다(자리값: 몸통 아랫면이 바닥에서 0.25m). 이 높이보다 낮은 턱과 계단은 걸리지 않고 넘는다. 몸통을 바닥에 끌면 가속과 감속이 설정값이 아니라 마찰 계수에 휘둘리고 계단에 걸린다. 물리로 움직이는 캐릭터에 널리 쓰는 방식이다(Toyful Games가 Very Very Valet에서 쓴 floating capsule).
- 다리는 물리 바디로 만들지 않는다. 몸 속도에 맞춘 절차 애니메이션으로 그리기만 하고, 떠 있는 몸통과 바닥 사이를 다리 그림이 채운다. 걷기 자체가 QWOP처럼 어려워지면 안 된다.
- 이동: 목표 속도를 향해 힘을 준다. 가속과 감속 값을 따로 두어 "출발이 느리고 멈출 때 미끄러지는" 정도를 수치로 조절한다. 미끄러운 바닥은 마찰 계수가 아니라 바닥 재질마다 둔 가속, 감속 배율로 만든다(자리값 0.2배).
- 직립 유지: 몸통 기울기에 PD 토크를 준다. 세기에는 능력표의 `balance` 값을 곱한다. 회전은 잠그지 않는다. 꼬리 무게와 반동이 균형에 영향을 줘야 한다.
- 점프: 바닥 감지(띄우는 데 쓰는 레이캐스트) 중일 때만 위로 임펄스. 뛴 직후 0.15초 동안은 띄우는 힘을 끈다(스프링이 점프를 도로 잡아당기지 않게). 발판 끝에서 떨어진 뒤 0.1초까지는 점프를 받아 주고, 착지 0.1초 전에 누른 점프는 착지하자마자 실행한다. 세 시간 모두 설정값.
- 방향 전환: 몸이 보는 방향이 바뀌면 꼬리 밑동이 붙는 엉덩이 위치와 관절 각도 제한이 좌우로 뒤집혀야 한다. 방법은 M2에서 두 가지를 만들어 보고 고른다. (가) 밑동 앵커를 0.2초에 걸쳐 반대쪽 엉덩이로 옮긴다(`setAnchor1`). (나) 밑동을 몸통 가운데에 두어 옮기지 않는다. 어느 쪽이든 각도 제한과 목표 자세에는 방향 부호를 곱해 쓴다.
- M1에서 정한 것: 레이캐스트는 몸통 축의 뒤, 가운데, 앞 세 줄이고 가장 가까운 바닥을 기준으로 띄운다. 직립 유지는 경사의 0.7배(자리값)만큼 눕는 것을 목표로 한다. 이동 힘은 몸통 중심보다 0.25m(자리값) 아래에 주어 출발할 때 앞이 들리고 멈출 때 쏠린다. 돌아설 때 머리는 목 앵커를 0.2초에 걸쳐 옮기면서 머리 바디도 같이 옮긴다(앵커만 옮기면 반동으로 몸통이 49도 돈다. known-issues 8번). 밑동을 옮기는 (가) 방법에서도 같은 문제를 확인해야 한다.
- 몸이 엎드린 형태인지 선 형태인지는 디자인이 정한다. 몸통 치수와 엉덩이 위치는 설정값이다(자리값: 몸통 길이 1.0m, 굵기 0.4m, 질량 3kg).
- 그림: 부위마다 이미지 키를 두고, 이미지 파일이 없으면 도형으로 그린다. 나중에 부위별 그림 파일만 넣으면 바뀌게 한다.

### 7.3 꼬리

- 마디 바디 여러 개를 회전 관절로 잇고, 첫 마디는 몸통 엉덩이에 붙인다. 관절마다 각도 제한을 둔다. 제한은 관절 하나에 90도보다 작게 잡는다(자리값 ±35도. 12마디면 꼬리 전체가 한 바퀴 넘게 말린다).
- 꼬리는 구간으로 나뉜다. 기본은 3구간 + 자를 수 없는 밑동. 구간 하나가 자르기 한 번이다. 구간 수와 구간별 마디 수는 설정값(자리값: 구간마다 3마디, 밑동 3마디, 꼬리 전체 1.5m, 마디 하나 0.1kg).
- 관절마다 모터가 "목표 자세"를 쫓는다. 모터 강성, 감쇠, 힘 상한(`setMotorMaxForce`)은 설정값. 힘 상한이 있어서 꼬리 끝이 목표를 늦게 따라가고, 무거운 걸 들면 처진다. 목표 각은 관절 제한 범위로 자른 뒤 모터에 넣는다.
- 조작 방식마다 다른 건 목표 자세를 누가 정하느냐뿐이다.
  - A 방식(마우스): 커서를 목표점으로 삼는다. 절대 방식은 커서의 월드 좌표를 꼬리가 닿는 반경 안으로 자른다. 상대 방식은 포인터를 잠그고 마우스 움직임으로 가상 커서를 옮긴다. 목표점에서 관절 각을 얻는 IK는 "고른 곡률" 방식으로 먼저 만든다. 모든 관절이 같은 각만큼 굽어 꼬리가 원호가 되고, 굽은 정도와 밑동 각 두 값만으로 끝이 목표점에 닿게 한다. 자세가 항상 매끄럽고, 목표점이 조금 움직였을 때 자세가 크게 튀지 않는다. 위로 굽는 해와 아래로 굽는 해 가운데 지금 꼬리 모양에 가까운 쪽을 고른다. FABRIK은 이 방식으로 모자랄 때만 붙인다.
  - A 방식의 개발자용 옵션으로 "IK 대신 끝 마디만 목표점 쪽으로 당기기"를 둔다. 이 힘은 몸 바깥에서 주는 힘이라, 상한이 몸무게보다 크면 꼬리로 몸을 끌어 올려 날 수 있다. 당기는 힘의 반작용을 엉덩이에 되돌려 알짜 힘을 0으로 만든다.
  - B 방식(자동): 평소에는 사인파로 살랑이는 자세. 공격 키를 누르면 정해진 휘두르기 동작을 재생하고, 잡기 키를 누르는 동안에는 가장 가까운 잡을 수 있는 대상 쪽으로 자세를 튼다. 움직이는 물건을 잡은 뒤에는 정해진 "들고 있는 자세"로 옮긴다(자리값: 꼬리 끝이 등 위 0.5m). A 방식에서는 커서가 이 일을 한다. 꼬리는 몸 뒤에 달려 있어서 휘두르기가 뒤쪽만 치면 마주 본 적을 칠 수 없다. 휘두르기가 닿는 범위는 설정값으로 두고, 자리값은 머리 위를 넘어 앞쪽까지다.
- 잡기와 걸기: 잡기 입력(A: 왼쪽 클릭 누르기, B: 잡기 키 누르기) 중에 꼬리 끝 감지 영역이 `grabbable` 대상에 닿으면 관절을 만들고, 입력을 떼면 끊는다. 고정된 대상(가지)이면 매달리고, 움직이는 물건이면 든다. 능력표에서 꺼져 있으면 관절을 만들지 않고 꼬리 끝만 꼼지락거린다. 물건을 꼬리로 감아 마찰로 드는 방식은 만들지 않는다(꼬리 끝 관절이 든다).
- 휘둘러 치기: 꼬리 마디가 물건이나 적에 닿을 때 마디 속도가 기준을 넘으면 "타격"으로 처리한다. 물건은 튕겨 나가고 적은 피해와 넉백을 받는다. A, B 모두 같은 판정을 쓰고, B는 휘두르기 동작이 속도를 만든다. 빠르게 휘두른 마디가 얇은 물건을 그냥 지나치면 꼬리 끝 쪽 마디에 CCD를 켠다(`setCcdEnabled`).
- 자르기: 꼬리 끝에서 구간 하나를 떼어 낸다. 떼어 낸 마디들은 서로 이어진 채 따로 떨어져 몇 초 꿈틀거리다 사라진다. 자른 뒤 꼬리 끝에 다시 자란 마디를 붙일 수 있게 한다(설정값, 자리값 0마디). 다시 자란 마디는 그림 키가 다르고 자를 수 없으며, 다음에 자를 때 앞 구간과 함께 떨어져 나간다.
- 안정성: 꼬리 끝을 가지에 걸고 몸이 매달리면 관절이 벌어져 꼬리가 늘어난다. 아래는 12마디 1.5m 꼬리에 3kg 몸을 매달고 5초 동안 잰, 관절 벌어짐 합계의 최댓값이다(꼬리 길이 대비. 앞은 가만히 매달림, 뒤는 수평에서 놓아 흔들림. Rapier 0.21.0).

  | 몸과 마디 하나의 질량 비 | 반복 4(기본값) | 반복 8 | 반복 16 |
  |---|---|---|---|
  | 60:1 | 17.0% / 32.4% | 4.3% / 11.4% | 1.1% / 3.6% |
  | 30:1(자리값) | 9.1% / 20.5% | 2.3% / 7.8% | 0.6% / 3.4% |
  | 20:1 | 6.5% / 13.2% | 1.6% / 5.0% | 0.4% / 2.4% |
  | 10:1 | 3.9% / 9.4% | 1.0% / 3.1% | 0.2% / 1.1% |

  대응 순서는 (1) `numSolverIterations`를 16으로 둔다. (2) 몸과 마디 하나의 질량 비를 60:1 아래로 둔다(자리값은 30:1). (3) 그래도 늘어나면 매달린 동안만 엉덩이와 꼬리 끝 사이에 최대 길이가 꼬리 길이인 rope 관절을 건다(60:1, 반복 8에서 가만히 매달릴 때 4.3% → 0.3%, 흔들릴 때 11.4% → 6.9%). 끝이 고정된 채 모터가 다른 자세를 고집해 떨리면 매달린 동안 모터 강성을 낮춘다.
- multibody 관절은 쓰지 않는다. JS 바인딩의 multibody 관절에는 모터와 각도 제한 메서드가 없고, multibody 꼬리의 끝을 가지에 건 채 흔들리면 속도가 발산했다(known-issues 2번).
- 위치 모터는 목표 각 179도까지 정상으로 쫓는다. 예전 버전에서 보고된 ±90도 문제는 0.21.0에서 재현되지 않았다. 다만 180도를 넘는 목표는 반대쪽으로 감긴다(200도를 넣으면 -160도로 간다). 목표 각을 관절 제한 범위로 자르는 이유다.

### 7.4 상태, 체크포인트, 회귀

- 게임 상태를 두 갈래로 나눈다.
  - `timeline`: 회귀하면 체크포인트 시점 값으로 되돌아간다. 예: 위치, 현재 방, 아이템, NPC 상태, 갈래 플래그.
  - `meta`: 회귀해도 남는다. 예: 남은 꼬리 구간, 회귀 횟수, 회귀를 넘어 기억되는 플래그.
  - 어떤 항목이 어느 쪽인지는 `state/schema.ts` 한 곳에서만 정한다. 기획이 바뀌면 여기만 고친다.
- 체크포인트: 설정된 계기(방 구간 입장, 특정 NPC와 대화 등)가 생기면 `timeline`을 통째로 복사해 시간순 목록에 넣는다. JSON으로 직렬화할 수 있어야 한다.
- 회귀 순서: 자르기 입력(길게 누르기) → 자르기 연출 → `meta` 갱신 → 회귀 지점 고르기 → 그 체크포인트의 `timeline` 복원, 그 뒤에 쌓인 체크포인트는 지움 → 방 다시 만들기 → 연출 끝. 연출은 자리표시(화면 깜빡임, 색 반전 정도)로 둔다.
- 방을 다시 만들면 상자 같은 물건은 체크포인트 시점의 위치가 아니라 방의 처음 배치로 돌아간다. 뼈대에서는 이렇게 단순하게 두고, 물건 위치까지 되돌려야 하는지는 기획이 정한다.
- 방에 놓는 것(NPC, 아이템, 물건, 적)마다 나타나는 회귀 횟수 범위를 둘 수 있다(`minRewinds`, `maxRewinds`. 자리값은 항상 나타남). 방을 다시 만들 때 `meta`의 회귀 횟수로 거른다. 회귀할수록 친구 NPC가 사라지고 상황이 달라진다는 기획(2절)을 데이터로 받는 자리다.
- 회귀 지점 규칙은 함수 하나로 바꿀 수 있게 한다.
  - `byCutCount`(기본, 자리값): k번째로 자르면 기록된 체크포인트 중 뒤에서 k번째로 간다. 없으면 맨 처음.
  - `playerChoice`: 기록된 체크포인트 목록에서 고른다. 이번에는 디버그 메뉴 수준으로만 만든다.
- 방 구간마다 배경 색조 값을 두어, 돌아갔을 때 어디로 왔는지 보이게 한다.
- 꼬리 구간 수가 바뀌면 능력표를 다시 읽어 바로 반영한다.

### 7.5 능력표

`src/config/abilities.json`에 남은 구간 수마다 값을 둔다. 기획이 정하기 전까지 기본값은 모두 같게 둔다. 그래서 처음에는 꼬리의 물리적 길이만 줄어든다. 능력 차이를 시험하고 싶으면 튜닝 패널에서 칸마다 끄고 켠다.

```json
{
  "3": { "canGrab": true, "canHang": true, "balance": 1.0, "whipPower": 1.0 },
  "2": { "canGrab": true, "canHang": true, "balance": 1.0, "whipPower": 1.0 },
  "1": { "canGrab": true, "canHang": true, "balance": 1.0, "whipPower": 1.0 },
  "0": { "canGrab": true, "canHang": true, "balance": 1.0, "whipPower": 1.0 }
}
```

### 7.6 최소 상호작용

- NPC: 감지 영역 + E 키 → 대화 상자. 대사는 `rooms.ts`에 넣은 자리표시 문장. 선택지를 고르면 플래그를 세운다(갈래 시험용). 대화 중에는 꼬리와 이동 입력을 막는다. NPC가 몇 번째 회귀까지 나오는지는 7.4의 회귀 횟수 범위로 정한다.
- 아이템: 닿으면 줍는다. 화면 구석에 개수를 표시한다. `timeline` 상태라 회귀하면 사라진다.
- 적(더미): 체력, 넉백, 단순 행동(가만히 / 좌우 왕복 / 다가오기). 토리가 맞으면 넉백만 있고 죽음이나 게임오버는 없다(미정이라서).
- 시간: `clock.ts`에 인터페이스만 둔다(`mode: 'off'`). 화면에는 아무것도 안 보인다.

### 7.7 디버그와 공유

- 키: F1 물리 디버그 그리기, F2 튜닝 패널, F3 조작 도움말, R 방 처음부터, 1~4 방 이동, Esc 일시정지. 노트북은 F1~F3에 Fn을 같이 눌러야 하는 경우가 많아, 화면 구석에 같은 일을 하는 작은 단추 세 개(디버그, 패널, 도움말)를 함께 둔다. 브라우저의 F1 도움말과 F3 찾기는 막는다.
- 상대 커서 방식(포인터 잠금)에서는 브라우저가 Esc를 잠금 해제에 먼저 쓴다. 잠금이 풀린 것(`POINTERLOCK_CHANGE`)을 일시정지 신호로 삼는다.
- 튜닝 패널: 모든 설정값, 조작 방식 A/B 전환, "지금 설정으로 링크 복사"(URL 파라미터로 인코딩), "설정 JSON 복사", FPS.
- URL 파라미터: `?scheme=A|B`, `?room=1~4`, `?cfg=<인코딩된 설정>`. `cfg`에는 기본값과 다른 항목만 넣고, 읽을 때 모르는 항목은 무시한다(빌드가 바뀌어도 예전 링크가 열리게).
- 화면 구석에 빌드 버전(커밋 해시 앞 7자리)과 현재 조작 방식을 작게 표시한다. 팀원이 어느 버전을 해 봤는지 말할 수 있게.
- 첫 화면(StartScene): 조작 방식 A/B 고르기와 키 안내. 게임을 잘 모르는 사람도 읽을 수 있는 쉬운 말로 쓴다.
- 터치 기기로 열면 "PC에서 열어 주세요" 안내를 띄운다.

## 8. 조작 (기본값, 바꿀 수 있음)

| 동작 | 키 |
|---|---|
| 이동 | A/D 또는 ←/→ |
| 점프 | Space |
| 말 걸기 | E |
| 꼬리 자르기(회귀) | Q 1초 누르기(게이지 표시) |
| 일시정지 | Esc |
| A 방식: 꼬리 움직이기 | 마우스 |
| A 방식: 잡기/걸기 | 왼쪽 클릭 누르는 동안 |
| A 방식: 공격 | 꼬리를 빠르게 휘두르기 |
| B 방식: 공격 | J |
| B 방식: 잡기/걸기 | K 누르는 동안 |

B 방식은 마우스 없이 키보드만으로 할 수 있어야 한다.

키는 글자가 아니라 키 위치(`KeyboardEvent.code`)로 받는다. 한글 입력 상태에서는 브라우저에 따라 글자 키가 다르게 들어올 수 있는데, 그때도 A, D, E, Q, J, K가 그대로 먹어야 한다.

## 9. 테스트 방 (스테이지가 아님)

1. 이동: 평지, 오르막과 내리막, 계단, 낮은 턱, 좁은 발판, 미끄러운 바닥 한 구간.

## 10. 마일스톤

마일스톤마다 배포 링크에서 바로 해 볼 수 있는 상태로 끝낸다. 개발자는 로컬에서 띄워 보지 않고 배포된 주소에서만 확인하므로 주소를 둘로 나눈다. `main`은 팀원이 보는 주소(https://soomin007.github.io/tori-prototype/)이고, `dev`는 개발자가 확인하는 주소(https://soomin007.github.io/tori-prototype/dev/)다. 작업은 `dev`에서 하고, 자동 확인과 브라우저 확인을 마치면 푸시해서 `dev/` 주소에 배포한다. 개발자가 그 주소에서 확인하고 좋다고 하면 `main`에 합친다. 만드는 중인 상태는 `main`에 올리지 않는다.

### 11.1 회의에 가져갈 질문

개발 쪽에서 답이 있어야 다음 일을 정할 수 있는 것들이다. 2026-11-25 회의록에서 답을 찾은 것은 2절로 옮겼고, 아래는 회의록에 아직 없는 것이다.

1. 발표가 12월 14일 주 가운데 정확히 언제이고, 그 자리에서 직접 시연하는지, 영상을 트는지, 링크를 내는지. 시연할 PC와 브라우저도 확인한다.
2. 토리의 몸이 엎드린 형태인지 선 형태인지, 몸 길이와 꼬리 길이의 비가 얼마인지. 회의록에는 참고 사진만 있고 토리 그림은 아직 없다. 물리 치수와 부위별 그림 규격이 여기서 나온다.
3. 꼬리를 다 자른 뒤에 관문에 막히면 어떻게 되는지, 전투에서 지면 어떻게 되는지. 짧은 꼬리는 닿는 거리가 줄어들기 때문에, 막혀서 꼬리를 자른 사람이 더 막힐 수 있다. 꼬리 길이마다 지나갈 길을 따로 만들어야 하는지가 여기서 정해진다.
4. 자른 뒤 꼬리가 얼마나 다시 자라는지. 길이를 되찾는지, 무늬만 달라지는지에 따라 꼬리 물리가 달라진다.
5. 비행을 직접 조작하게 할지, 엔딩 장면으로만 보여 줄지. 조작으로 넣으면 뼈대에 없는 물리가 하나 더 필요하다.
6. 발표에 낼 범위. 10분 안에 스테이지가 몇 개 들어가는지, 보스전을 넣는지, 스테이지마다 NPC가 몇 명이고 어느 회귀에서 사라지는지. 뼈대 뒤에 남는 날은 5일이다(10절).

## 12. 위험 요소

- 일정: 뼈대만으로 12월 8일까지 가고, 그 뒤 5일에 발표용 내용을 모두 붙여야 한다. 10절의 줄이는 순서를 따르고, 12월 4일~5일 회의에서 발표 범위를 작게 잡는다.
- 꼬리 체인이 몸무게를 못 버팀: 실측으로 대응 순서를 정했다(7.3). 꼬리나 몸의 질량, 마디 수를 바꿀 때마다 매달리기 테스트를 다시 돌린다.
- 몸은 키보드, 꼬리는 마우스, 거기에 실시간 전투까지 하면 손이 바빠 피로할 수 있다(회의록에서도 나온 걱정). M4 손 확인 항목으로 확인해 회의에 가져간다.
- 꼬리를 직접 다루는 조작(A 방식)이 팀 테스트에서 너무 어렵다고 나올 수 있다. 그때는 B 방식으로 간다. 회의록의 초기 범위 메모도 꼬리를 복잡한 물리 없이 길이별 수치로만 만드는 쪽이었다.
- 먼저 만든 쪽이 기획을 끌고 가는 문제: A/B를 같은 완성도로 만들고, 팀에는 "아직 정해지지 않은 비교용"으로 소개한다.
- Phaser 4, Vite 8, TypeScript 7은 나온 지 얼마 안 돼, AI가 예전 방식의 코드를 쓸 수 있다. 타입 검사와 `node_modules/phaser/skills/` 확인으로 막는다(known-issues 4번).
- 성능: 꼬리 마디 수, 물건 수에 상한을 두고 튜닝 패널에 FPS를 띄운다.
